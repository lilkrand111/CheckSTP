# Проект проверки технической документации

Состояние документа: 21.11.2026. Документ описывает текущую реализацию и решения
для продолжения разработки в новом чате. Операторские команды — в
[BACKEND.md](../BACKEND.md), интерфейс и его интеграция — в
[FRONTEND.md](FRONTEND.md), инструкции для ИИ-разработчика — в
[AGENTS.md](../AGENTS.md).

## Назначение и границы MVP

Пользователь загружает курсовую или другую техническую документацию в DOCX.
Система проверяет доступные по структуре документа требования оформления СТП,
возвращает замечания, по отдельному запросу исправляет поддерживаемые нарушения
и повторно проверяет исправленную копию.

Реализованы FastAPI-бэкенд и адаптивный интерфейс CheckSTP по макету Forma.
Фронтенд — HTML, CSS и JavaScript-модули без сборки и внешних зависимостей;
страницу `/` и `/assets/` отдаёт FastAPI с того же origin, что и API. Подготовлены
Dockerfile, Compose с Caddy и изолированная сквозная проверка. Настройка VPS,
DNS и публичный запуск — отдельный этап; см. [DEPLOYMENT.md](DEPLOYMENT.md).

Используется один СТП 01–2017 с согласованными уточнениями заказчика.
В реестре 31 правило с ID F01–F36, исключая F11, F13, F14, F17 и F21.
Наличие правила в реестре не означает полного покрытия требования:
например, F16 отложено, а многие проверки покрывают только структурные признаки.
Точное покрытие описано в `formal_check/coverage.py`.

В этой версии отсутствуют:

- смысловой анализ и обращения к LLM;
- OCR и распознавание содержимого изображений;
- рендеринг DOCX, вычисление фактических страниц и геометрии вёрстки;
- пересчёт полей и содержания Word;
- аккаунты, восстановление доступа, общая история загрузок в API;
- база данных, внешняя очередь и распределённая обработка.

Модули смыслового анализа могут быть добавлены отдельным этапом. Не включайте
их в формальную проверку и не представляйте их как готовую возможность.

## Обработка документов

FastAPI принимает DOCX в память. Один Uvicorn координирует до MAX_CONCURRENT_JOBS
дочерних процессов. При проверке worker получает исходные байты через stdin и
возвращает проверенный JSON. При исправлении он заново инспектирует исходные
байты, применяет поддержанные правки, проверяет сохранность содержимого и
выполняет полный formal_check исправленной копии. Вкладка получает отчёт и копию
одним ответом. Клиентские фрагменты и номера страниц для правок не используются.

На сервере отсутствует архив документов. Подписанная cookie и CSRF защищают
обе операции. IP для ограничения нагрузки находится в памяти. Серверный профиль
исключает том для загрузок, журналы запросов и swap для контейнеров.
Условия для хоста перечислены в [инструкции VPS](VPS_RUNBOOK.md).

## Нормы и автоисправление

Текущая версия проверяющего модуля — `0.3.7`, набора требований —
`stp-01-2017-2026-11-06`. Версия HTTP-приложения — `0.1.0`.
Не путайте их и не используйте только название СТП как версию алгоритма.

В `0.3.6` переписаны тексты `actual`, `expected` и `section` без изменения норм,
статусов и операций исправления. Правила для текстов замечаний: простые короткие
утвердительные предложения, без длинного тире (короткое тире в диапазонах вроде
«14–16 пт» допустимо), без слов «распознанный», «секция», «блок» и названий
внутренних структур DOCX. Параметры страницы одной секции DOCX показываются как
«Параметры страницы», при нескольких секциях добавляется «раздел Word N», как
в интерфейсе Word. Нулевые интервалы в описании F07 не перечисляются. Проверка
текстов: `tests/test_messages.py`.

В `0.3.7` исправлены два бага классификации и мест без изменения норм:

- подпись рисунка, набранная двумя абзацами («Рисунок 2.3 – Графическая» +
  «интерпретация метода Ньютона»), больше не даёт замечаний F03/F04/F06 по второму
  абзацу. Он получает вид `caption_continuation`, если подпись не закончена,
  следующий абзац стоит сразу за ней, выровнен по центру, начинается со строчной
  буквы, короче 150 знаков и не заканчивается точкой;
- у абзаца со своим текстом и встроенной формулой (например, подписи) в `context`
  больше не пишется «Формула: позиция N…». Подсказка позиции остаётся только
  у формул и абзацев без собственного текста;
- формула, набранная обычным текстом, распознаётся не только по «=», но и по
  «≈ ≠ ≤ ≥ ≡ ∏» (при менее чем четырёх русских словах). Такая строка больше не
  получает замечаний F03/F04/F06 как обычный текст.

Тексты `0.3.7`: пропуск в нумерации называет соседние номера («После рисунка 2.3
идёт рисунок 2.5.», формулы в скобках); повтор номера: «Номер рисунка 4.9 встречается
дважды.»; F32 называет первую пару источников не по порядку и отмечает только их;
F30 различает отсутствующий и неверно записанный статус; несколько пустых абзацев
после заголовка (F07) или между рисунком и подписью (F22) без других интервалов
описываются как «2 пустых абзаца» с требованием оставить один. Статусы не менялись.

В подписях F22 и F23 дефис «-» с пробелами между номером и названием допустим
наравне с тире «–» и «—» (решение заказчика от 06.11.2026); замечания на него нет.
Проверяется редакция СТП 01–2017; ссылки студентов на другие редакции стандарта
значения не имеют.

Набор `stp-01-2017-2026-11-06` уточняет по решению заказчика от 06.11.2026:

- F22: один пустой абзац между встроенным рисунком и подписью оценивается так же,
  как пустая строка после заголовка в F07: одинарный интервал, «Перед» и «После»
  0 пт, без интервала после рисунка и перед подписью. Иначе `error`. Исправитель
  использует ту же операцию `blank_gap_spacing`, что и F07: меняет интервалы пустого
  абзаца и, при необходимости, соседних. Абзац с рисунком он не меняет: если
  у рисунка есть свой интервал после, промежуток не исправляется и замечание
  остаётся. Подпись, над которой стоит обычный текст без рисунка, даёт `review`
  «Над подписью нет рисунка». Если выше стоит нераспознанный объект (OLE, VML),
  замечание не выдаётся.
- F10: если в документе нет ни одного колонтитула, отсутствие автоматического
  номера страницы — `error`. При наличии колонтитулов без поля PAGE — `review`.
- F04/F05: исправитель ставит тот из допустимых отступов 12,5 и 12,7 мм, который
  чаще встречается в обычном тексте документа; при равенстве или без данных 12,5 мм.

Основания правил зафиксированы в `formal_check/standards.py`. В частности,
одинарный интервал F03 — согласованное уточнение заказчика; оно не должно
представляться фронтом как дословная норма самого СТП.

Поддерживаются F01, F03, отдельные нарушения F04–F07 и пустая строка F22. Исправитель выбирает
только безопасные операции со статусом `error`. Не исправляются `review`,
`recommendation`, шрифты и неподдержанные объекты. Точный список операций —
`formal_fix/operations.py:ALLOWED`; определять исправляемость по одному ID нельзя.
Для F05 разрешена специальная замена пробельного разделителя номера табуляцией;
не следует обещать побайтовую неизменность всего извлечённого текста копии.
Слова и нумерация защищаются проверками исправителя.

Если исправлять нечего, сохраняется копия, совпадающая с исходником побайтово.
Успешное исправление не гарантирует отсутствия оставшихся замечаний. Изменения
полей и интервалов могут сдвинуть страницы; окончательную вёрстку проверяют в Word.

## Интерфейс

Клиент хранит данные открытых документов в памяти вкладки. Контракт операций
и правила отображения отчёта приведены в [описании интерфейса](FRONTEND.md).
